# Multi-unit product review — October 14, 2026

Results must let shoppers verify a printed product quantity of two or more, whether charged on separate rows or on one row. A correct multiplication does not establish that the shopper bought that count.

Previously, `RECEIPT_PROMPT` required two independent product charge rows and explicitly excluded single quantity-two rows. `normalizeReceipt` rejected singleton model candidates, recovered only identities with multiple product rows, and dropped groups with fewer than two remaining rows. A unit test and live synthetic check enforced that exclusion. The mobile Results screen only renders returned `duplicateGroups`, so an extracted five-unit tea row could be absent from its checklist without being explicitly marked as an expected purchase.

The prompt and normalizer now accept one product row with an explicit quantity of at least two. The server also adds that row when extraction preserves the quantity but omits the candidate. Overlapping proposals merge once. Single-unit or unknown-quantity rows alone, pack sizes, free rows, fees and summaries do not independently qualify. Corrections leaving zero or one known unit suppress the review; uncertain corrections retain a partial review without an amount. Known printed quantities remain available when prices are unreadable.

For the supplied receipt's financial rows, the existing Results UI displays two product groups: A2 Organic Whole Milk (two separate $5.99 rows) and Golden Oolong Tea (`$1.69 each · 5 on receipt`). The tea remains one review card and one extracted product row, with its $0.25 deposit linked. The `5 @ $1.69` and `5 @ $0.05` annotations do not become separate charges, and Total Bottle Deposit remains a summary. If four teas were actually bought, the conditional one-unit difference is $1.69 plus $0.05 deposit. No actual purchased quantity can be established from the photo.

The existing checklist uses a looks-correct checkbox with review/undo, not a numeric purchased-quantity input. This change exposes the recorded count for manual comparison and retains `verificationStatus: unverified`. It does not add a confirmed-error or refund state. Existing API fields, routes, model settings, privacy policies and separate analysis/lookup accounting are unchanged. No mobile layout change is required.

Regression coverage includes the transcribed financial rows (no receipt photo or payment identifiers stored), singleton candidates and deterministic fallback, five deposit allocations, four-versus-five conditional math, unknown/inconsistent prices, corrections, non-product quantities, existing review/undo presentation, the shared prefixed HTTP route with mocked Responses, and the compiled mobile client against the synced shared normalizer. These checks do not establish live OCR accuracy on the attached photo.

Backend runtime is synced to Little Moments using `pnpm backend:sync-little-moments`. Validation passed: 97 Receipt Decoded tests, 79 Little Moments tests, 15 shared integration tests, TypeScript in both repositories, and the mobile/shared-server contract check. All providers were mocked. `scripts/live-receipts.mjs` now expects one review group for the quantity-two synthetic image; the earlier live-validation JSON remains a historical record. No live provider call, push, deployment or hosted setting change is part of this update. Existing production clients receive the broader review behavior only after the shared backend is deployed and the receipt is analyzed again.
